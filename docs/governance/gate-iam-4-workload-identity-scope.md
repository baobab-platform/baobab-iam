## 1. What already exists (verified against source)

**`baobab-iam`** already wires `actor_type=workload` via a hardcoded-claim protocol mapper (`config/scopes/actor-type-workload.json`) attached to all 6 `*-workload.json` clients, and grants `context:resolve` as a default scope. `scripts/bootstrap.sh` imports client scopes before clients and no longer double-processes workload clients (a fixed bug, gate-iam-0-discovery R-2/§4.9). `tests/integration/run.sh` §4 already decodes and asserts `actor_type`/`scope`/`iss` on an issued workload token; §8 already asserts independent per-client revocation.

**`baobab-cp`**'s `internal/auth/oidc.go` `Verify()` already enforces `actor_type ∈ {human, workload}`, a `tenant_id` shape check, a ≤15-minute token lifetime (ADR §26), and scope-format validation, and delegates `aud` checking to `go-oidc`'s built-in audience match against a single configured `WorkloadOIDCAudience` (default `baobab-control-plane`). `router.go`'s `authorize()` gates `/v1/context/resolve` and `/v1/resolve` on `actorType=workload` + `context:resolve` scope + non-empty `tenant_id`/`azp`. `WorkloadOnlyProvisioningPolicy` (Gate IAM-3 machinery, not this gate's) auto-provisions a canonical `Principal` for workload actors on first sight.

**`baobab-platform/shared`** already has most of what ADR-0007 §100 asks `shared` to define: `contracts/control-plane/v1/access-token-claims.schema.json` (the exact §18 claim shape, `aud`/`actor_type` required), `contracts/authorization/v1/scope-registry.yaml` (partial — `context:resolve`'s entry already declares `audience: ["baobab-control-plane"]`, confirming the target audience string phase 1 uses below), `contracts/authorization/v1/delegation.schema.json` (full delegation-metadata contract, already citing ADR-0007 §13-18/§108), `contracts/identity-events/v1/workload-revoked.schema.json`, and `contracts/control-plane/v1/security-policy.yaml` (already declares `transport.workload_to_control_plane.mtls_required: true` with `termination_owner: baobab-platform/infrastructure`, matching the ADR's ownership split exactly).

## 2. Gaps against ADR-0007 (by repository)

### `baobab-iam`
1. **No `aud` claim mapper on any workload client** (§24-25) — no `oidc-audience-mapper` existed anywhere in `config/`. Every workload token was missing the audience claim `go-oidc` requires, which — combined with gap 2 below — meant neither of `baobab-cp`'s two workload endpoints was reachable end-to-end with a real IAM-issued token. **Fixed in this PR** (§4, phase 1).
2. ~~No `tenant_id` claim mapper~~ — **not a gap to fix this way; see §3.** The original discovery pass proposed adding a static per-client `tenant_id` mapper. Reading ADR-0007 §87-91 directly (not just the summary) shows this is the wrong fix: the ADR explicitly prohibits baking a fixed tenant into a workload's identity. This becomes its own phase (§4, phase 4) once `baobab-cp`'s enforcement model is redesigned, not a claim-mapper addition here.
3. ~~No machine-readable workload registry~~ — **fixed**, `baobab-platform/shared#31` (the registry itself) + `baobab-platform/baobab-iam` phase 3 (consuming it — see gap 5).
4. **No per-endpoint expected-`azp` mechanism** (§20) — Keycloak includes `azp` in client-credentials tokens by default; nothing needs adding on the IAM side, but nothing on the `baobab-cp` side checks it against an expected value either (gap 7).
5. ~~`tests/integration/run.sh` didn't assert `aud`~~ — **fixed**, phase 1 (§4 assertion) and phase 3 (§9: cross-checks every `config/clients/*-workload.json` against the registry in both directions — orphaned local client, or a registry entry with no matching client — and §10: cross-workload `azp`/`sub` isolation, ADR §102's impersonation category). Still not covered: "wrong-environment credential rejected" — this realm has no environment-separated workload clients yet (Gate IAM-2 work, not built), so there's no real infrastructure to test against; documented as deferred rather than faked.

### `baobab-cp`
6. **No registry-based workload allowlist** — any token from the configured issuer/audience with a valid `actor_type=workload`/scope/non-empty `tenant_id` passes; no per-client authorization exists (§42-44, and §99's "canonical workload identity" ownership).
7. **No `azp`-specific expected-value enforcement** at any endpoint (§20).
8. **No integration tests** covering the §102 token-validation/isolation negative cases (wrong audience, wrong azp, wrong actor type, revoked credential, cross-workload impersonation) — only unit tests of the verifier/router logic exist.
9. **`tenant_id` is trusted directly from the token as the sole tenant-authorization signal** — see §3. Confirmed by reading the actual handlers, not inferred: `api/context.go`'s `resolveContext` passes `principal.TenantID` straight into `a.store.ResolveContext(...)` as the tenant to resolve against; `api/resolver_handler.go`'s `ResolverHandler.Resolve` accepts an optional request-body `tenant_id` but only to **reject** it if it disagrees with `principal.TenantID` (line 41-44) — it never uses a request-supplied or policy-resolved tenant as the actual source of truth. Both endpoints treat "the workload's own static token claim" as "the tenant this request is authorized for."

### `baobab-platform/shared`
10. ~~`scope-registry.yaml` is incomplete~~ — **fixed**, `baobab-platform/shared#31`. `contracts/control-plane/v1/openapi.yaml` used `mapping:read/write/approve/resolve` and `market:read/write/approve`, none of which were defined in the registry (ADR §22-23: "exact scope names SHALL be defined in `baobab-platform/shared`"). All 7 now added, cross-checked against each endpoint's actual `adminOidc`/`workloadOidc` requirement in `openapi.yaml`.
11. ~~No workload-registry contract~~ — **fixed**, `baobab-platform/shared#31`. Added `contracts/identity/v1/workload-registry.yaml`, one entry per known workload with the full §42 registration field list. Modelled as a plain YAML registry (matching this repo's existing convention — `scope-registry.yaml`/`reason-code-registry.yaml` have no companion `.schema.json`), not a JSON Schema + instance pair as originally proposed below in phase 2's description; the plan text undersold what the repo's own conventions already called for.
12. ~~`security-policy.yaml`'s `required_claims` omits `azp`~~ — **not a gap; correction.** The original plan (phase 2 below) proposed adding `azp` to the global `required_claims` list. Drafted, then reverted before pushing (`baobab-platform/shared#31`'s PR description) after re-reading ADR-0007 §20 directly: `azp` "SHOULD" identify the granted client and is only ever an *expected-value* check on specific sensitive endpoints ("Sensitive internal APIs MAY require an expected azp... where the policy is endpoint-specific") — not a blanket requirement for every token, human tokens included. `access-token-claims.schema.json` already correctly models it as optional; `security-policy.yaml` was right to omit it. The real mechanism stays per-endpoint `azp` enforcement in `baobab-cp` against the new registry (phase 4, gap 7), not a contracts change.
13. **No workload-tenant-entitlement contract** — needed once §3's redesign lands, to describe how a workload's permitted tenants are declared/resolved (CapabilityBinding-style), not part of `workload-identity.schema.json` today.

## 3. Architectural finding: workload identity ≠ tenant access (ADR-0007 §87-91)

The original discovery pass characterized "no `tenant_id` claim mapper in `baobab-iam`" as a straightforward missing-claim gap, matching what `baobab-cp`'s current code expects. Reading ADR-0007 §87-91 directly instead of that summary shows the code itself has the mismatch, not `baobab-iam`'s config:

> §87 Workload Context Resolution: `Workload token → CP validates iss/aud/exp/actor_type/azp/scope → Canonical workload resolution → Requested tenant/entity/context → Policy decision`
> §88 Context SHALL Be Explicit: "`baobab-trade` may operate across multiple tenants, but each request SHALL resolve a permitted tenant context."
> §90 Workload Scope and CP Context: authorization SHALL combine *IAM scope* + *Control Plane context* — `scope: context:resolve` "means the client may invoke the resolver. It does not mean all tenants are authorized."
> §91 No Scope-to-Tenant Shortcut: "This is prohibited: `scope=context:resolve → allow requested tenant`. The requested tenant SHALL still be evaluated."

A single client-credentials token per workload client cannot carry "the one tenant this workload is allowed" as a static claim — engines like `baobab-trade` serve many tenants from one workload identity, and the ADR's own flow diagram puts "requested tenant" and "policy decision" as steps *after* workload identity is established, not encoded inside it. `baobab-cp`'s current code (gap 9) does exactly what §91 prohibits: it uses the token's own `tenant_id` claim as the tenant-authorization decision itself, with no separate policy/entitlement step.

**Decision (made 2026-09-10, via explicit check-in):** ship the unambiguous ADR §24-25 fix (the `aud` claim mapper, gap 1) now as phase 1, and treat the tenant-context/entitlement redesign as its own dedicated phase (§4, phase 4) once the registry (phase 2-3) exists to build the entitlement check against, rather than bolt an ADR-violating `tenant_id` mapper onto `baobab-iam` in the meantime. `baobab-cp`'s two workload endpoints remain unreachable with a real per-tenant request until phase 4 ships — this was already true before this session (gap 1 alone blocked them), so phase 1 doesn't regress anything; it only fixes the audience half of the blocker.

## 4. Phased plan

Bounded, one concern per PR, matching this session's established pattern.

1. ~~**`baobab-iam` — `aud` claim mapper.**~~ **Done — `baobab-platform/baobab-iam#8`.** Adds an `oidc-audience-mapper` (`aud=baobab-control-plane`) directly to the `context:resolve` client scope — every workload client that already carries that scope (all 6) picks it up with one change, matching `baobab-platform/shared`'s existing `scope-registry.yaml` declaration for `context:resolve` exactly, no per-client duplication needed. Adds an `aud` assertion to `tests/integration/run.sh` §4. Does **not** touch `tenant_id` (§3) or `azp` (Keycloak already includes it by default; nothing to add here). CI caught a real bug mid-phase: the scope's new description exceeded Keycloak's `client_scope.description` `VARCHAR(255)` limit, which failed scope creation server-side and was silently swallowed by `bootstrap.sh`'s `|| echo "...may already exist"` fallback — fixed same-PR by shortening it.
2. ~~**`baobab-platform/shared` — contract completion.**~~ **Done — `baobab-platform/shared#31`.** Filled in the `mapping:*`/`market:*` scopes in `scope-registry.yaml`; added `contracts/identity/v1/workload-registry.yaml` enumerating the 6 known workloads (`baobab-cms`, `baobab-erp`, `baobab-pulse`, `baobab-trade`, `thamani-backend`, `zuribeans-backend`) with their audiences/scopes/owner/environment/rotation-owner (§42's full field list) — as a plain YAML registry, not a JSON Schema + instance pair (see gap 11's correction). Did **not** add `azp` to `security-policy.yaml`'s `required_claims` (see gap 12's correction) — drafted, then reverted after re-reading ADR-0007 §20 directly.
3. ~~**`baobab-iam` — workload registry as source of provisioning.**~~ **Done — `baobab-platform/baobab-iam#10`, with a design correction.** The plan as written proposed having `scripts/bootstrap.sh` fetch the registry itself. That's infeasible by this repo's own deliberate design: `bootstrap.sh` runs *inside* the built Keycloak container, and the Dockerfile's `tools-build` stage comment explains `curl` was removed from that image on purpose (3 unfixed HIGH-severity ubi9 CVEs) — adding it back just for this would undo a real security decision. Instead, the registry cross-check lives in `tests/integration/run.sh` (§9), which already runs host-side/CI-side with real network access and already declares exactly that requirement in its own header comment. §9 fetches the registry (pinned in the new `contracts.lock.yaml`, bumped past a placeholder v1.2.0 pin that nothing had ever consumed) and cross-checks it against every `config/clients/*-workload.json` in both directions (an unregistered local client, or a registry entry with no matching client) — matching by `clientId` *content*, not filename, since two of the six client files (`thamani-backend-workload.json`/`zuribeans-backend-workload.json`) don't carry the `-workload` suffix in their actual `clientId` (a real, deliberate pre-existing naming asymmetry, `gate-iam-0-discovery.md` §4.9). §10 adds the `azp`/`sub` cross-workload isolation case from §102. Running §9 locally against the real registry caught a genuine bug in phase 2's own data (the registry used `thamani-backend-workload`/`zuribeans-backend-workload` as keys, not the real `-workload`-less client IDs) — fixed as `baobab-platform/shared#32`, with `contracts.lock.yaml` bumped again past it before this phase's own PR.
4. ~~**`baobab-cp` — no-claim workload tenant reconciliation.**~~ **Done — `baobab-platform/baobab-cp#102`.** Narrower than the redesign originally scoped here (see §8 for why): fixes the specific ADR-0007 §87-91 defect (gap 9) directly, without waiting for the full `CapabilityGrant`/entitlement model. `router.go`'s `authorize()` no longer requires `principal.TenantID != ""` for workload actors; a new `resolveWorkloadTenant(principalTenant, requestedTenant)` helper is the single reconciliation rule used by all five workload-gated endpoints (`/v1/context/resolve`, `/v1/resolve`, `/v1/platform-context/resolve`, `/v1/capabilities/resolve`, `/v1/capabilities/resolve-batch`): when the token carries its own `tenant_id`, a request-supplied tenant must still match it (spoofing protection unchanged); when it carries none — the real-world case, since no `baobab-iam` workload client mints one, see §3 — the request-supplied tenant (or, for the two `capabilities/resolve*` endpoints, the already-validated `context_id`'s own tenant) is honored instead. Registry-based per-client allowlisting (gap 6), `azp` expected-value enforcement (gap 7), and the §102-category integration tests (gap 8) remain open but are separable hardening, not blockers to workloads being reachable at all — tracked as follow-on work in `baobab-cp`, not this gate.
5. **Workload lifecycle states** (§45: `PROVISIONED/ACTIVE/SUSPENDED/REVOKED/RETIRED`) — fold into phase 2's registry schema (a `status` field) and phase 4's enforcement (reject non-`ACTIVE`); blocked on phase 4 for the same reason.

Each phase gets its own PR, full local validation before push, and a check-in loop to green/merge before the next phase starts — the same discipline used for Gate IAM-3's 6 phases.

## 6. Phase 4 paused pending the `ADR-BCP-*` series (2026-09-11)

Before implementing phase 4 (the `baobab-cp` tenant-context redesign, §3/§4), I asked whether to (a) build a new per-request-tenant + workload-entitlement mechanism now, (b) use a simpler static per-workload tenant allowlist in the registry, or (c) descope tenant authorization from this gate entirely. The answer: wait — `baobab-cp` has 8 more new ADRs coming (a new `ADR-BCP-*` series) that should be read together with ADR-0007 first.

Checking `baobab-cp`'s `docs/adr/` confirmed why this matters: two of that series already exist on `main` (commits `9759813`/`8e39c5c`-adjacent, added directly by the repo owner, not through this session) — `ADR-BCP-001` (a parent DB-migration/Go-architecture spec, ~5500 lines) and **`ADR-BCP-002` — "Capability-Centric Baobab Platform Architecture and Digital Estate Consumption Model"** (~3160 lines). ADR-BCP-002 already defines, in detail, exactly the mechanism phase 4 would otherwise have had to invent from scratch:

- **§14 Capability Grant Model**: a tenant-scoped `CapabilityGrant{tenant_id, capability_id, scope_id, source, status, effective_from/to, constraints, ...}` that "SHALL answer whether a capability may be consumed" — this *is* the workload-entitlement check phase 4 needs, already scoped as a first-class Control Plane concept, not something to bolt onto `router.go` independently.
- **§15-17 Capability Binding Model / Binding Modes / Provider Registry**: `CapabilityBinding` is being remodelled as fulfillment-only ("A binding SHALL NOT itself grant entitlement") — directly relevant since `baobab-cp`'s existing `domain.CapabilityBinding` (used today in the `/v1/resolve` pipeline) is exactly what this ADR says will be reshaped.
- **§28 Authorization Boundaries**: explicitly assigns "platform entitlement, CapabilityGrant, CapabilityBinding, provider selection" to the Control Plane layer, and "workload identity" to IAM — confirming the ownership split ADR-0007 §99 already implied, but with the actual entitlement data model now spelled out.
- **§66 Migration Strategy** lists its own `Gate 0/1/2...` sequence (distinct from this programme's `Gate IAM-N` numbering) — implementation here should land within that sequence, not ahead of it.

Building phase 4's tenant-check against `router.go`'s current shape now would very likely fight or duplicate `CapabilityGrant` once the remaining 8 `ADR-BCP-*` documents land and this model is finalized. **Phase 4 is paused** until that series is available to read in full alongside ADR-0007. Phases 1-3 are unaffected (they're `baobab-iam`/`shared` work, already merged) and gap 5 in `baobab-platform/shared` (a workload-tenant-entitlement contract) is now understood to likely belong to the `ADR-BCP-*`/`CapabilityGrant` model rather than a new bespoke schema — revisit once that series lands.

## 7. The full `ADR-BCP-*` series landed (2026-09-11) — bigger than Gate IAM-4 anticipated

`ADR-BCP-003` through `ADR-BCP-009` (7 more documents, ~22,600 lines) landed on `baobab-cp`'s `main` directly. A background research pass (targeting BCP-003 "Capability Registry, Grants, Scopes, Bindings and Deterministic Resolution Model," BCP-007 "Control Plane APIs... and Service-to-Service Consumption Model," and BCP-009 "Capability-Centric Security, Isolation, Residency, Revocation and Failure Semantics," cross-referenced against the real current code) confirmed §6's read was directionally right, but the actual scope is substantially larger than "redesign two endpoints":

**`CapabilityGrant` is tenant-to-capability only — never workload-specific.** Its finalized schema (`ADR-BCP-003 §9-12`, matching the suggested `capability.capability_grant` table) is `{id, tenant_id, capability_id, scope_id, source_type, source_reference, status, effective_from, effective_to, constraints, granted_by, revoked_at, revoked_by, version, created_at, updated_at}` — no `workload_id`/`client_id`/`principal_id` field anywhere. ADR-BCP-002 §5.6 is explicit: "A grant answers: *May this tenant consume this capability?* A grant SHALL NOT determine which engine instance provides it." The workload/caller check is a **second, orthogonal** step the pipeline (`ADR-BCP-004 §52`) calls "Validate principal ↔ tenant relationship" — and **the ADR-BCP series requires this step but never once defines its schema or storage** (confirmed by grep: zero matches for `Membership`/`TenantMembership`/`workload_tenant`/`principal_tenant` across all nine documents beyond the one-line pipeline mention). The closest existing candidate is `baobab-platform/shared`'s pre-existing (pre-BCP) `contracts/identity/v1/membership.schema.json` — structurally a good fit, but not cited or endorsed by the new ADRs, so using it is an inference to validate, not something the ADRs authorize outright.

**None of this exists yet in `baobab-platform/shared`.** Grepping all of `contracts/` for `CapabilityGrant`/`capability_grant`/`CapabilityBinding`/`capability_binding` returns zero matches. The entire capability/grant/binding/provider contract layer ADR-BCP-002 §66 Gate 1-2 and ADR-BCP-003 §101 Gate 1 call for is still unstarted, in `shared` and in `baobab-cp`'s own persistence (no `..._capability_grants.sql` migration exists; `internal/repository` has no `CapabilityGrantRepository`).

**The ADRs define their own gate sequence, and Gate IAM-4 phase 4's work sits downstream in it, not at the front.** Three overlapping sequences exist (`ADR-BCP-002 §66`, `ADR-BCP-003 §101`, `ADR-BCP-007 §161`); the most relevant is ADR-BCP-007's own 19-gate plan, where "IAM Workload Integration" (token validation, audience, workload identity, coarse scopes, delegated principal handling — essentially this phase's own scope) is **Gate 6**, explicitly sequenced *after* Gate 1 (Shared canonical contracts), Gate 2 (Context API remodel), and Gate 3 (single capability resolution). None of Gates 0-5 have started.

**What's confirmed already correct and needs no change:** `baobab-iam` phases 1-3 (client/scope/registry work) are unaffected and orthogonal to all of this — ADR-BCP has nothing to say about workload *client* provisioning, only about what a validated workload may then do. `baobab-cp`'s `internal/auth/oidc.go` `Principal`/`Verify()` also needs no change: `TenantID` is already correctly optional there (validated only if present); the defect is entirely downstream in `router.go`'s `authorize()` (which wrongly *requires* `TenantID != ""` for workload actors) and in `api/context.go`/`api/resolver_handler.go` (which trust that claim as authorization instead of treating a request-supplied tenant as an unvalidated hint, per `ADR-BCP-007 §11`'s explicit "the word `hint` is intentional" framing).

**Decision (made 2026-09-11, via explicit check-in): wait for `baobab-cp`'s Gates 0-5.** Phase 4 stays blocked rather than shipping a narrow interim fix — the alternative (`ADR-BCP-007 §160`'s allowance for a time-bounded adapter validating a request-supplied tenant against `Membership` as a stopgap) was considered and explicitly declined, given the risk of throwaway work if `Membership` isn't the mechanism the still-unwritten principal↔tenant design eventually lands on. `baobab-cp`'s two workload endpoints remain unreachable with a real multi-tenant request until that foundational work lands and reaches Gate 6 ("IAM Workload Integration") — this was already true before Gate IAM-4 started (gap 1, the missing `aud` claim, blocked them independently) and phases 1-3 already fixed everything on `baobab-iam`'s side of the boundary, so nothing here regresses.

**Gate IAM-4 is effectively complete for now.** Phases 1-3 shipped everything this gate can deliver without `baobab-cp`'s own architecture work landing first. Re-open phase 4 once `baobab-cp`'s `ADR-BCP-*` Gates 0-5 are done (watch for a `CapabilityGrantRepository`/`..._capability_grants.sql` migration and `baobab-platform/shared` contracts for `CapabilityGrant`/`CapabilityBinding` as the signal) — re-read this document's §7 findings at that point rather than re-deriving them, and confirm what mechanism ended up implementing the principal↔tenant relationship check before touching `router.go`/`context.go`/`resolver_handler.go`.

## 8. Phase 4 shipped directly — `baobab-cp`'s own concurrent rebuild didn't cover it (2026-09-11)

`baobab-cp`'s `ADR-BCP-*` Gates 0-5 work (tracked in `baobab-platform/baobab-cp#72`, 20 sub-issues) proceeded at very high velocity after §7 was written — PRs #83 through #101 merged within a few hours, covering `CapabilityGrant`/`CapabilityBinding`/`CapabilityScope`/`CapabilityProvider` domain modeling, persistence, and runtime APIs. That session's own tracking comment on `baobab-platform/baobab-cp#74` asserted: *"IAM boundary (ADR-BCP-009 §5-7) confirmed already correctly implemented via existing OIDC verifiers; no changes needed there."*

Direct inspection of the resulting code (`api/router.go`'s `authorize()`, `internal/service/context_resolution_service.go`) showed that claim was correct against what it checked — ADR-BCP-009 §5-7 (general OIDC verification: `iss`/`aud`/`exp`/signature) — but did not address this gate's own, more specific requirement: ADR-0007 §87-91's "No Scope-to-Tenant Shortcut." The defect §3/§7 identified was still fully present: `authorize()` still rejected every workload request with an empty `tenant_id` claim outright (`principal.TenantID == ""` → 403), and `ContextResolutionService.Resolve` still read `principal.TenantID` directly as the authorization signal. Since no `baobab-iam` workload client mints a `tenant_id` claim (§3), all five workload-gated endpoints remained completely unreachable by any real workload token — unchanged from §6/§7's finding, and not touched by any of #83-#101 despite the surrounding rebuild.

**Why ship now instead of continuing to wait for Gates 0-5:** the §7 decision to wait was specifically to avoid duplicating or fighting the *entitlement* model (`CapabilityGrant`: does this tenant have this capability). That model landed in #83-#101 and is real, but it is deliberately narrower than what phase 4 needs at the boundary — `CapabilityGrant`'s finalized schema (`ADR-BCP-003 §9-12`) is tenant-to-capability only, with no `workload_id`/`client_id`/`principal_id` field, and ADR-BCP-002 §5.6 is explicit that a grant "SHALL NOT determine which engine instance provides it." The specific gap this gate owns — a workload token with no tenant claim being unable to present *any* tenant at all — sits one level below entitlement, at request admission. Waiting for `CapabilityGrant` enforcement (still not hard-enforced platform-wide per `baobab-platform/baobab-cp#86`) would have kept the endpoints at a hard 403 indefinitely for a reason unrelated to entitlement. `baobab-platform/baobab-cp#102` fixes only that admission-level gap and deliberately does not touch or duplicate `CapabilityGrant` enforcement (see PR description's "Deliberately not touched"), so it does not fight the Gates 0-5 work landing around it.

**What's still open, and correctly deferred (unchanged from §7):** `CapabilityGrant` tenant-to-capability entitlement enforcement remains opt-in (`baobab-platform/baobab-cp#86`); the principal↔tenant relationship mechanism `ADR-BCP-004`'s pipeline diagram references (which tenants a given workload identity may legitimately act for, beyond "whichever one the caller supplies") is still undefined by the ADR-BCP series — the same gap §7 flagged, now confirmed to still be genuinely unwritten rather than something #83-#101 covered under a different name. Both are `baobab-cp`-owned follow-on work, tracked there, not blockers to this gate.

**Gate IAM-4 is done.** All 4 phases are merged: phases 1-3 in `baobab-platform/baobab-iam` (`#8`, and the `baobab-platform/shared`/`baobab-platform/baobab-iam` registry work), phase 4 in `baobab-platform/baobab-cp#102`. Every workload-gated resolution endpoint is reachable end-to-end by a real IAM-issued workload token for the first time, with the ADR-0007 §91 scope-to-tenant-shortcut prohibition honored and all pre-existing spoofing/cross-tenant protections unchanged.
